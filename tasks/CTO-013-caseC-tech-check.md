期限：ASAP
用途：內部查核，供 COO 修正對外回覆；不代表已承諾承接、報價或交付。

## 〇、為什麼要做

案C的功能需求包含模型路由、備援與費用控制，但「零延遲」「100% 精確」沒有明確量測定義。若直接接受或直接斷言不可能，都可能誤導對方。本任務先查清技術邊界，再決定回覆如何寫。查核完成並經 COO 複核前，不發出任何案C對外回覆。

## 一、目標

獨立判斷五組待查核主張是否成立、在哪些條件下成立，以及原說法是否過度。不要為董事長或 COO 的既有看法找支持；能反駁就反駁。交付結果必須足以讓 COO 改寫成可驗收的需求，並刪除不成立的技術斷言。

## 二、範圍

納入：路由延遲、跨模型與同模型跨供應商的備援及上下文處理、重試與平行呼叫的費用計量、Redis 送出前額度檢查、預定回覆用語查核。

不納入：程式實作、正式壓測、登入或付費操作、實際模型呼叫、取得客戶資料、聯絡任何外部對象、報價、接案承諾、部署或發布。只使用公開可讀的官方資料。本單對案件只使用「案C」，不得加入真實案件編號、客戶或平台名稱。技術產品及模型供應商名稱可用於來源比對。

## 三、背景與材料

以下案情由 COO 轉述，並非 CTO 已讀取原始提案或既有系統。你不需要也不得假稱看過其他對話、附件、原始碼或後台。

### 3.1 案C功能摘要

- 多模型 AI Router，依問題類型、成本、健康狀態等權重選擇模型。
- 模型或供應商失效時自動備援、重試。
- 費用計量與額度控制。
- 使用 Redis 分散式鎖，在送出前做 0.01 秒的超額預檢／斷路控制。
- 管理後台。
- 對方提出「零延遲」「100% 精確」。這兩者的量測起訖、指標、容錯範圍與適用對象尚未定義；不得自行把「精確」等同模型回答正確率。
- 既有應用、後台、部署環境、API 與費用資料來源未知。

### 3.2 董事長看法，列為待查核主張而非結論

- AI Router 不可能達到字面上的 100% 無延遲。
- 即使使用同一模型，切換不同供應商仍可能有上下文連結問題。

### 3.3 預定對外回覆要點，尚未發送

R1：延遲目標應量化，而不是只寫「零延遲」。
R2：精確度必須定義量測對象與容許誤差。
R3：備援時的上下文處理必須定義清楚。
R4：既有應用與管理後台的現況未知，不能直接保證整合範圍。

這是回覆要點，不是已完成或已核准的回覆全文。請逐點查核，不要聲稱已審查不存在的完整回覆。

## 四、查核需求

### Q1：路由與「零延遲」

待查核句：「路由加入不可避免的延遲，所以零延遲不可行。」

1. 區分字面端到端 0 毫秒、路由增量開銷、相對既有流程不增加可感知延遲，以及透過路由降低總回應時間。不可把不同定義混為一談。
2. 拆開規則判斷、分類器／模型判斷、健康檢查、排隊、網路、重試等環節，說明哪些在關鍵路徑、哪些能快取或非同步處理。
3. 說明「增加處理步驟」是否足以支持「總延遲一定更高」；提出反例與適用邊界。
4. 比較純規則與小模型分類器做路由決策本身的延遲數量級。分開本地與遠端部署、冷啟動與暖啟動、模型推論與網路往返；可引用有條件的官方資料或提出估算區間，但沒有依據就標未驗證，不得當作案C實測結果。
5. 建議可驗收指標：路由本身耗時、首個 token 時間、完整回應時間；列明量測起訖、p50／p95／p99、負載與重試是否計入。沒有實測不得提出保證數字。

### Q2：備援與上下文連續性

待查核句：「不同模型，以及同模型不同供應商之間，無法無縫維持上下文；必須重送歷史並付出延遲與 token 成本。」

1. 分別評估跨模型與同模型跨供應商，不得只評估其中一種。
2. 比較訊息格式、system／developer 指令、工具呼叫及結果、多模態內容、session／server-side state、prompt cache、context window 與模型版本。標示可轉換、可攜、不可攜或來源不足。
3. 區分「應用程式保存並重送對話歷史」「供應商保存的會話狀態」「模型回答語意一致」。API 格式相容是否等於上述三者都相容？
4. 查核「歷史一定必須重送」「一定失去上下文」「一定額外收取完整歷史 token 費」是否過度；檢查無狀態 API、狀態 API、共用歷史儲存、快取與供應商計費規則的差異。
5. 評估可以做到的連續性程度、需要的轉接／重播機制、截斷或摘要策略，以及重試在串流中斷、工具已執行時的副作用與重複執行風險。不得把可重建歷史說成保證回答相同。
6. 對同模型跨供應商，明列哪些 cache／session 狀態會遺失、哪些可由應用程式重建。以明確的歷史 token 數、快取命中條件與官方費率，給出額外 token／費用的計算方法；對重播增加的延遲提供有依據且附條件的數量級，資料不足則標未驗證。不可捏造通用成本或時間。
7. 選至少兩個有官方公開文件的供應商做具體比對。「同模型」若無法確認精確版本與供應方式，明列未驗證，不得以相似商品名稱當作相同版本。

### Q3：費用計量與「100% 精確」

待查核句：「重試、失敗與平行多模型呼叫下，費用無法 100% 精確。」

1. 區分送出前預估、API 回傳 usage 後的計量、供應商帳務對帳、內部帳本正確性。判斷每一層可達到什麼，不得籠統否定全部。
2. 查核失敗／逾時／取消但供應商已處理、串流缺少最終 usage、重試、平行呼叫、快取、計價版本與四捨五入的影響。逐項附官方依據，無資料則未驗證。
3. 提出 request／attempt ID、冪等紀錄、額度預留、usage 結算與帳務對帳如何配合；說明哪些是設計推論，不能冒充已驗證實作。
4. 回答合理誤差如何定義與測量：誤差分母、期間、金額或比例、未結算項目、對帳後殘差。若公開資料不足以給通用百分比，直接寫「無法給通用誤差值」，提供校準方法，不得捏造 ±1% 等數字。
5. 提出至少一組可驗收的計量規格。所有數字若只是建議，標示「建議值，需實測／雙方確認」，不得寫成產業保證。

### Q4：Redis 與 0.01 秒送出前阻擋

待查核句：「用 Redis 分散式鎖可以在 0.01 秒內完成送出前超額阻擋／斷路。」

1. 明確換算 0.01 秒 = 10 毫秒，並定義時間範圍：Redis 指令執行、往返、鎖等待，或完整送出前檢查？是否包含排隊、跨區與重試？
2. 區分費用額度門禁與供應商健康狀態 circuit breaker。分散式鎖、原子檢查與扣留額度各解決什麼問題？不能只用一個名稱替代完整機制。
3. 評估原子檢查加預留額度、併發競態、鎖逾時、Redis 故障、網路分割、複寫與切換、熱點及最差情況。比較分散式鎖與原子操作／腳本的適用條件，不先指定哪一種必定正確。
4. 明確回答「包含網路往返的完整 Redis 預檢能否在 10 毫秒內完成」，分同機／同區／跨區與有無鎖競爭給出成立條件或資料缺口。區分「一般條件下可能低於 10 毫秒」與「所有情況下保證低於 10 毫秒」。官方效能資料不等於案C環境已壓測。
5. 說明額度不足、狀態未知、Redis 不可用時的 fail-open／fail-closed 取捨，以及使用者等待與停止送出的規則。
6. 說明如何處理送出前未知的最終費用：預估、最大額度預留、完成後結算、取消與退款。若無供應商硬限制支援，不能把「阻擋已知超額」說成「保證最終絕不超額」。
7. 提供壓測與故障測試計畫：拓樸、網路距離、併發、p99、超時、故障注入、額度越界率與測試期間。列出實測前不可承諾的項目。

### Q5：逐句修正預定回覆

1. 對 R1 至 R4 逐點給出「可保留／需限定條件／需改寫／應刪除」，附原因、證據與可直接採用的修正版。
2. 同時審查 Q1 至 Q4 的待查核句。若 CTO 發現董事長或 COO 用語錯誤、概括過度或混淆概念，直接指出。
3. 回覆應解釋技術邊界並提出如何驗收，不挖苦對方，不用「絕對不可能」替代定義與證據。
4. 列出仍需向對方確認的最小資訊集合，但不得聯絡對方，也不得以等待這些資訊為由停止其餘查核。

## 五、交付物

一次完成整份報告，再做一次整體自檢。不要分階段等待核准。

1. 一頁結論置於最前：五組判斷、對外不可承諾項目、可以採用的條件式規格，以及待 COO 裁決事項。
2. 證據表：主張編號、原句、已驗證／未驗證／推論、成立條件與反例、官方文件名稱、精確 URL、章節、必要短引文、文件版本或版本未知、查核日期。
3. 技術說明：按 Q1 至 Q5 展開，明確寫出機制，而不只列技術名稱。
4. 回覆修正表：R1 至 R4 及各待查核句的原句、處置、修正版與證據編號。
5. 驗收建議：延遲、上下文、帳務、額度門禁的量測方式、測試條件與未確定參數。
6. 「待 COO 裁決」：資料不足、互相衝突、需案C環境實測的項目；每項說明缺什麼、影響什麼，其餘工作照常完成。
7. Markdown 報告與 JSONL 證據逐筆資料，直接以附件交回董事長轉交 COO。Markdown 在通訊附件中可命名為 .md.txt。不交 docx、Excel、ZIP，不使用 Google Drive 連結代替附件。

JSONL 每筆至少包含：task_id、version、case_code、claim_id、original_claim、verdict、conditions、counterexample、source_title、source_url、source_section、source_quote、source_version、checked_date、recommended_wording、remaining_gap。來源不足時欄位可為 null，verdict 必須寫未驗證。每筆只能是一個可獨立查核的主張，不把多個判斷塞進同一筆。

- Q1 至 Q5 全數回答，沒有把待查核看法當作前提。

- 精確區分零延遲的不同定義、跨模型與同模型跨供應商、預估與實際帳務、額度門禁與健康斷路。
- 數字有量測依據或清楚標為建議；不編造通用誤差或效能保證。
- 能直接支持 COO 修正回覆，並提出可執行的驗收方法。
- Markdown 與 JSONL 的主張編號、判斷、證據和修正版一致。
